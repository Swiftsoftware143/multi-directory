🔑 API Keys Setup Guide

Everything a VA needs: which key goes where, how to get each one, and how to prove it works.

⬇️ Download this guide (PDF) Download the API keys setup guide as a PDF, or read the full guide below. Or press Ctrl+P / ⌘P for a clean printed copy.

⚡ Walkthrough — do this, in this order

For administrators and VAs wiring providers into the admin panel — the order to do it in.

1

Sign in to the Admin Panel. Open https://zaarhub.com/admin-panel.html and sign in as an administrator.

2

Find the card for your provider. Use Where each control lives in the Admin Panel to jump to the card that owns the key you have.

3

Get the key from the provider. Follow the provider's block below to the exact screen where the key is generated, and copy it.

4

Paste it into the panel — not a file. Credentials belong in the admin panel (the database), never in code and never in server-wide environment variables. Enter the key in that provider's card and save.

5

Test the capability, not just the save. Trigger the feature that uses the key (a search, an email, a payment) and confirm it works end to end.

6

Check availability flags. Providers marked Required must be configured before launch; Optional ones enrich results but degrade gracefully when absent.

7

Leave the rest unconfigured if you like. An unconfigured optional provider must log and skip — never break the page.

8

See the result. Every capability you switched on is reachable from a UI control in the admin panel, and a real request proves it works.

✅ You're done when: every required key is entered in the admin panel, and a real call through each configured capability succeeds.

How keys are stored (read this once)

  • All keys are pasted in one place: the Admin Panel (admin-panel.html), card 🔑 Provider API Keys. Every provider has its own block.
  • Every key can be named. Type a name in the “Name this key” field (e.g. Primary, Test account), paste the key next to it, then press ＋ Add key. You can store several keys for the same service — each one appears on its own line with its name and masked value.
  • Exactly one key per service is the Default (blue badge) — that is the one the platform uses. Press Set as default on another line to switch. Delete one key with Delete on its line; the other keys for that service stay.
  • Keys are saved per tenant, encrypted at rest, and always displayed masked (first 4 + last 4 characters). Nobody — including you after saving — can read a key back out of the panel.
  • The provider badge shows the state at a glance: Not set or N keys. The Test button on a key line tests the default key for that service and prints the real API answer at the bottom of the card.
  • Where a provider needs more than the key itself, the block grows an extra input field and the label on that field tells you what it wants — Base URL for most providers, Search Engine ID (Google Custom Search), or DataForSEO login (account email) for DataForSEO, whose second credential is the account email rather than a web address. Don't skip it — the integration will not work without it.
  • Stuck on where to create one? Every provider block has a “How do I get this key? →” link that jumps straight to that provider's section on this page.
  • Never put a real key in a ticket, chat, email or screenshot. If a key leaks, rotate it in the provider's console and paste the new one.

✉️ Email / SMTP card — how to configure it

Email settings are per directory. The card sits directly under Provider API Keys in admin-panel.html.

  1. Pick the directory in the first dropdown.
  2. Pick the transport in the Transport field. The list is read live from the email service itself, so it always matches what the server can actually send with — today smtp, mailgun, sendgrid, sendiio. The badge next to the directory dropdown shows the service status and the same list.
  3. SMTP → fill SMTP host, SMTP port (587), SMTP username, SMTP password and Encryption (STARTTLS / SSL / None).
    Mailgun / SendGrid / Sendiio → leave the SMTP fields as they are; the API key those transports need is the one you saved in the Provider API Keys card above (Mailgun, SendGrid, Sendiio).
  4. Fill From name, From email and (optional) Reply-to, then press Save settings. The card shows ✓ Saved (transport: …) when it lands.
  5. The password is write-only: the card shows write-only on the field and never displays a saved password. Leave it blank and save to keep the stored one.
  6. Press Verify credentials (real check) — this performs a real SMTP login / real API credential call and prints the service's own answer (ok, skipped or error plus detail) in the box below. A canned “success” is never shown.
  7. Put your own address in Send a real test email to… and press Send test email. {"status":"sent"} in the box means mail actually left the server; “skipped / directory_not_configured” means the save above did not land.

💳 Payment Gateways card — Stripe & PayPal

Customers pay through Stripe and/or PayPal. The card sits under Provider API Keys in admin-panel.html and writes the payment_providers settings. Two values are needed per gateway: the API key that creates the checkout, and the webhook verification value that proves an incoming “payment complete” message really came from the gateway.

Why the second value is mandatory: the webhook endpoint is public (the gateway has to reach it without a login). Without a verification value the server cannot tell a real payment notice from a forged one, so it refuses every event instead of marking orders paid. That is why the card — and the API behind it — will not let you switch a gateway to Active until the verification value is stored.

  1. Stripe. In Stripe → Developers → API keys copy the Secret key (sk_live_… or sk_test_…). Paste it into API key / client credentials.
  2. Stripe — webhook. Go to Stripe → Developers → Webhooks → Add endpoint. In Endpoint URL paste the address the card shows (the line under the form: <your-domain>/api/v1/webhooks/stripe). Under Events to send tick checkout.session.completed and checkout.session.expired. Save, then press Reveal next to Signing secret and copy the whsec_… value into Webhook signing secret.
  3. PayPal. In PayPal → Apps & Credentials open your app (Live or Sandbox) and put Client ID and Secret into the card joined by a colon: client_id:secret in API key / client credentials.
  4. PayPal — webhook. Still in the app, scroll to Webhooks → Add Webhook, set the Webhook URL to the address the card shows (<your-domain>/api/v1/webhooks/paypal) and tick PAYMENT.CAPTURE.COMPLETED and CHECKOUT.ORDER.APPROVED. After saving, copy the Webhook ID of that webhook into PayPal Webhook ID (PayPal has no signing secret; it verifies each event server-side against this ID).
  5. Set Environment: Test / sandbox while you are testing (sandbox keys and the sandbox webhook), Live for real customers. Sandbox and live are different worlds — a sandbox webhook is never accepted in Live.
  6. Set Status to Active and press Save gateway. The row at the top of the card must show credentials saved and webhook verifiable. If you try to activate without the verification value the card refuses and tells you which value is missing.
  7. Send a real test payment and check the row list: webhook verifiable plus the checkout session flipping to completed is the proof it works end to end. Rejected events are stored too — they are the fastest way to see a wrong signing secret.
  8. Both fields are write-only: they are encrypted at rest and never shown again. Leave a field blank and save to keep the stored value.

One gateway is enough to sell; the checkout form uses whichever gateway is Active. Deleting a gateway stops new checkouts but never deletes past orders.

🔎 Discovery queue — review before adding

Google Places results are never dumped straight into the directory. They land in a queue you review first (ZaarHub Admin → Populate Businesses).

  1. Pick the Directory and the City, then pick a category — the search query is filled in for you as <category> <city>. You can still edit the query.
  2. Press Search & add to queue. The rows appear in 2 · Queue — review, then add; the counts line shows in queue · franchise · already listed.
  3. Each row shows the business name, address, rating/review count, its auto-mapped category (change it in the row's Category dropdown at any time), and its badges: Franchise (big chain) and Already listed (duplicate of a business already in that directory).
  4. Franchise and already-listed rows are unticked by default. Select all eligible ticks everything else; tick a franchise row yourself if it really is a local business you want.
  5. Press ＋ Add selected to directory. The status line reports added / skipped and then re-reads the directory to confirm the businesses are really there. Clear queue empties the rows that are still waiting.
  6. Reloading the page is safe — the queue is stored server-side per directory and comes back exactly as you left it.

🚀 Start here — VA checklist

Work top to bottom. After every save, click Test on that row and confirm it reports the key as configured before moving on.

  1. Get admin access. Log into the Admin Panel at admin-panel.html with the admin account (not a business/portal account).
  2. Open the key card. Find the card titled 🔑 Provider API Keys (use the panel nav bar to jump to it). It lists every provider below with a live Not set / N keys badge. Name each key in the “Name this key” field before you press ＋ Add key — names are how you tell two accounts of the same service apart.
  3. Google Places first — it is the one that is actually broken right now. Create a Google Maps Platform → Places API key and paste it (see Google Places). This unblocks Populate / business discovery.
  4. AI drafting. Paste a DeepSeek key (the default AI provider) or an OpenAI / Anthropic key. Without one of these, AI blog/content drafting cannot run.
  5. System email. If the directory sends newsletters, notifications or receipts, paste Mailgun, SendGrid or Sendiio — then open the ✉️ Email / SMTP card, pick that transport for the directory and press Verify credentials, then Send test email (steps). SMTP needs no provider key at all: just host/username/password on the same card.
  6. Card payments. If the directory takes card payments or pays out, paste the Stripe secret key.
  7. SMS. If the directory texts customers, paste the Twilio credentials (and complete carrier/A2P registration).
  8. Captured leads → CRM. For CoreSwift, paste only the csk_… key — the hub URL is preconfigured. (Advanced: paste a Base URL too if you run a self-hosted CoreSwift.)
  9. Optionals. Add BrightLocal / Yext / Uberall / SerpAPI / Google Custom Search / Bing / Telnyx / GrooveSell / SAM.gov / USAspending only if the client actually uses them.
  10. Verify. Click Test on every configured key line (it calls GET /api/v1/admin/provider-keys/<provider>/test and prints the real API answer), press Verify credentials + Send test email on the Email/SMTP card, then run one real end-to-end action per feature: one Populate search (queue → add selected), one AI draft, one test email, one test payment, one test SMS.

Bing Web Search API (Azure Cognitive Services)

1. What it powers

  • Alternate search/discovery source.

2. How to get the key

  2. Create a Bing Search resource under Cognitive Services (Bing Search v7) — this requires the Azure subscription to have a payment method attached.

Azure bills per transaction for the Bing Search resource; a free/low-cost tier may be offered depending on region and offer. A credit card is required to create the resource. Verify on the Azure pricing page.

6. How to verify it

Click Test on the row (GET /api/v1/admin/provider-keys/bing/test).

🔑 DataForSEO Optional dataforseo

Keyword ideas and search volume for the Blog/QA keyword tool

1. What it powers

  • The Blog & QA keyword tool when the keyword source is set to DataForSEO (POST /api/v1/blog-qa/fetch-keywords with source: "dataforseo").
  • Nothing else — every other feature keeps working without it.

2. How to get the credentials

  1. Sign in at app.dataforseo.com.
  2. Open API Access (dashboard). It shows your login — which is the email address on the account — and your API password.
  3. Copy both. DataForSEO uses HTTP Basic auth, so the pair is used as login:api password. This is a separate password from the one you sign in with, and it can be regenerated on that page.

3. Where to paste it

Admin Panel → card 🔑 Provider API Keys → DataForSEO row:

  • Paste API key field → the API password from the API Access page (stored encrypted at rest).
  • the extra field, labelled “DataForSEO login (account email)” → your account email. It is not a web address, even though it travels in the same column as the other providers' Base URLs.
  • press ＋ Add key.

4. Required or optional — and what breaks without it

Optional. Without it, choosing the DataForSEO keyword source returns “DataForSEO is not configured…” and suggests the other keyword sources (AI-generated or AnswerThePublic).

5. Cost & plan notes

DataForSEO is prepaid pay-as-you-go: you buy account balance and each keyword request draws from it. There is a minimum top-up and no free tier, so confirm the client wants paid keyword data before buying balance.

6. How to verify it

The Test button (GET /api/v1/admin/provider-keys/dataforseo/test) only proves the key is stored — it returns the masked preview and does not call DataForSEO, so it cannot tell a wrong pair from a right one.

To prove the credentials really work, run a keyword fetch with source: "dataforseo". A wrong login / API password (or an empty account balance) comes back as DataForSEO refused the request (HTTP 401) — regenerate the API password on the API Access page and paste it again. A working pair returns keyword rows instead of that error.

🔍 Google Custom Search Optional google_cse

Programmable Search Engine JSON API

1. What it powers

  • Content Research → Google Custom Search integration (Programmable Search Engine JSON API).
  • Alternate search/discovery source.

2. How to get the key

  1. Sign in to Google Cloud Console and pick (or create) a project.
  2. Go to APIs & Services → Library, search for Custom Search API and click Enable.
  3. Go to APIs & Services → Credentials → Create credentials → API key and copy it.
  4. Create the search engine itself at programmablesearchengine.google.com (Add / Create a Programmable Search Engine).
  5. Open the engine's Setup / overview and copy its Search engine ID — this is the cx value.

3. Where to paste it

Two values go in. Admin Panel → card 🔑 Provider API Keys → Google Custom Search row: paste the API key into “Paste API key” and the Programmable Search Engine ID into the extra field labelled “Search Engine ID (cx)” → Save.

Extra field: this provider also needs “Search Engine ID (cx)” — paste it into the extra input on its row, not into the key field.

4. Required or optional — and what breaks without it

Optional. This provider is one of the few that needs two values — the API key and the cx Search Engine ID. A key without the cx will not work.

5. Cost & plan notes

The Custom Search API is free up to a daily query quota, then billed per 1,000 queries; the Programmable Search Engine itself is free. Check the current quota on the Google Cloud Custom Search pricing page.

6. How to verify it

Click Test on the row (GET /api/v1/admin/provider-keys/google_cse/test) and confirm the masked key preview comes back.

🗺️ Google Places Required google_places

Local business data API — listings, reviews, citations

⚠ The key currently stored is INVALID. Google replies 400 The provided API key is invalid. for search?query=dental&city=palm-bay. This key must be replaced by a fresh Google Maps Platform → Places API key created with the steps above. Until then, business discovery is broken.

1. What it powers

  • ZaarHub Admin → Populate tab → Search Places — the city + category + radius business search that finds businesses and publishes them to the directory.
  • Place autocomplete and place details lookups when adding a business by hand.
  • Business enrichment in the Data Company module (phone, website, hours, reviews).
  • The scraper/discovery source list as the google_places source.

2. How to get the key

  1. Sign in to Google Cloud Console with the Google account that owns (or will own) the billing.
  2. Create a project (or pick an existing one) for this directory — e.g. Multi-Directory Places.
  3. Enable billing on that project. Google Maps Platform keys are free-tier-with-credit-card: you must attach a card, you get a recurring free credit, and usage above it is billed per request.
  4. Go to APIs & Services → Library, search for Places API and click Enable (enable Places API (New) too if it is offered — the search uses the Places endpoints).
  5. Go to APIs & Services → Credentials → Create credentials → API key.
  6. (Recommended) Click Edit API key and add an Application restriction (HTTP referrers for your admin domains, or the server IP) and an API restriction limited to Places API. This limits the damage if the key leaks.
  7. Copy the key — it starts with AIza…. Never paste it into a ticket, chat or email.

3. Where to paste it

Admin Panel (admin-panel.html) → card 🔑 Provider API Keys → the Google Places row → paste into the “Paste API key” field → Save. The same key can also be pasted from ZaarHub Admin (zaarhub-admin.html) → Populate tab → “Google Places API Key” field → Save Key. Both write the same stored key.

4. Required or optional — and what breaks without it

Required for Populate / discovery. Without a valid key the Populate search and place details return nothing and the Data Company enrichment cannot resolve a provider.

5. Cost & plan notes

Google Maps Platform requires a billing account with a credit card. A recurring monthly free credit is applied, then requests are billed pay-as-you-go. See the current credit and per-request rates on Google's Maps Platform pricing page — do not rely on remembered numbers.

6. How to verify it

On the Google Places row click Test → GET /api/v1/admin/provider-keys/<provider>/test returns the masked key preview, never the raw key. For a real end-to-end check open ZaarHub Admin → Populate → Test Key, which actually calls Google Autocomplete (POST /api/v1/zaarhub/admin/provider-keys/google-places/test) and fails loudly if the key is invalid.
